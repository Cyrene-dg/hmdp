# 青禾茶饮会员营销平台一期需求基线 v1.0

> 项目范围：优惠券权益与门店履约模块  
> 文档状态：模拟场景基线，可用于设计与 Mock 验证，不代表真实甲方确认  
> 背景声明：“青禾茶饮”及相关组织、系统和业务数据均为项目推演设定  
> 变更原则：进入技术设计后，范围或核心规则变化需要记录影响并更新版本
> 当前权威需求：本文件已由[完整 PRD v1.0](./青禾茶饮_优惠券权益与门店履约模块_PRD_v1.0.md)细化；发生冲突时以 PRD v1.0 为准

## 1. 一期目标

在不重建会员中心、小程序、POS、ERP 和供应链系统的前提下，为十家试点门店跑通以下闭环：

```text
总部配置免费券活动
→ 会员领取并查询最终结果
→ 权益进入会员卡包
→ 试点门店在线验券和核销
→ 核销及撤销数据与 POS 日文件核对
→ 一致记录形成加盟补贴待结算明细
```

一期解决的主要问题：重复领取和超发、页面成功但权益未到账、POS 重复核销或结果未知、平台与 POS 数据无法核对。

## 2. 项目和个人职责边界

- 项目名称：青禾茶饮会员营销平台；
- 当前负责范围：优惠券权益与门店履约模块；
- 本模块负责活动权益配置、会员领取、权益状态、POS 履约、异常记录和结算候选明细；
- 会员中心仍是会员身份权威来源；
- POS 仍负责门店收银订单；
- ERP 仍负责财务入账和实际付款；
- 小程序负责页面展示，本模块提供接口。

## 3. 一期角色

| 角色 | 一期主要操作 |
|---|---|
| 市场人员 | 创建活动、配置权益内容和领取规则 |
| 运营人员 | 配置试点门店、查看领取与核销情况、处理业务异常 |
| 财务人员 | 审核单张补贴金额、核对差异、确认结算批次并导出明细 |
| 客服人员 | 根据申请号、会员号或券码查询结果，不直接修改财务记录 |
| 会员用户 | 查看活动、提交领取、查询结果和查看卡包 |
| POS 终端 | 验券、核销、查询原结果和申请当天原单撤销 |
| 系统管理员 | 配置外部系统凭证、试点门店和基础权限 |

## 4. 一期纳入范围

1. 十家可完成 POS 升级的试点门店，暂按五家直营、五家加盟设定；
2. 免费领取类优惠券或指定商品权益；
3. 活动草稿、提交审核、审核通过、发布、提前结束；
4. 活动时间、总库存、每会员限领一次和适用门店配置；
5. 活动发布前为全部加盟门店配置同一单张补贴金额，直营门店补贴固定为 0；
6. 会员身份校验与平台短期会话；
7. 领取资格校验、库存预留、防重复领取、异步发放和失败补偿；
8. 领取结果查询和用户卡包；
9. POS 在线验券、核销、原结果查询；
10. 当天、原单、未锁定结算的核销撤销；
11. POS T+1 对账文件幂等导入；
12. 一致记录进入待结算，差异记录冻结并进入异常清单；
13. 按活动、门店和批次导出结算复核明细；
14. 关键操作日志、异常查询和基础监控。

## 5. 一期排除范围

1. 付费购券、支付、退款和资金清结算；
2. POS、会员中心、小程序点单系统和 ERP 的重建；
3. 离线核销以及断网后先核销、再补传；
4. 跨日核销自动撤销；
5. ERP 自动入账和加盟商自动付款；
6. 历史优惠券全量迁移；
7. 原料、仓储、配送、制作、排班和外卖履约；
8. 积分商城、会员成长和复杂营销自动化；
9. 博客、点赞、关注、Feed、签到等社区能力；
10. 全部门店一次性切换和真实生产 SLA 承诺。

## 6. 已冻结的一期规则

### 6.1 活动和门店

- 直营门店由总部统一配置参加；
- 一期加盟试点门店由甲方线下确认后导入；
- 同一活动内全部加盟门店使用相同单张补贴金额；直营门店补贴金额为 0，不生成补贴候选；
- 活动发布后，权益内容、领取上限、适用门店和单张补贴金额不得直接修改；
- `SCHEDULED` 或 `ACTIVE` 活动仅允许增加库存，不允许减少；每次增加都必须走新的审批并形成不可变的库存调整记录；
- `ENDED` 或 `TERMINATED` 活动不得再追加库存；
- 活动开始后门店退出不能删除历史适用关系，异常情况进入运营处理。

### 6.2 会员领取

- 小程序传入的会员编号不能作为可信身份；
- 会员 Token 经会员中心验证后，平台建立短期会话；
- 一期默认同一会员在同一活动中最多领取一次；
- 请求被受理不等于领取成功；
- 只有用户权益已经创建且卡包可查询，才对外返回领取成功；
- 发放失败需要完成库存与领取占位补偿后，才能进入最终失败；
- 相同领取请求号重复调用返回首次处理结果。

### 6.3 POS 履约

- 验券只返回当前状态快照，不锁定权益，也不保证后续一定核销成功；
- 核销请求必须携带稳定且唯一的 POS 请求号；
- 相同 POS 请求号重复调用返回首次结果；
- 不同请求同时核销同一权益，只允许一个成功；
- 核销响应丢失后，POS 必须查询原请求结果，不得盲目创建新请求；
- 一期不支持离线核销。

### 6.4 撤销与结算

- 在线撤销限当天、原单且结算尚未锁定；
- 撤销产生独立流水，原核销记录不得删除；
- 权益尚在有效期时可恢复为可用，已经过期时保持过期；
- 跨日或结算锁定后的撤销转人工差异处理；
- 全部门店的平台成功核销都进入 T+1 对账；
- 直营门店对账一致后完成核对但不生成补贴明细；加盟门店对账一致后才由补贴候选生成待确认结算明细；
- 状态不一致的记录进入差异清单，不自动计算为应付补贴；
- 财务按完整结算批次确认；批次必须排除直营记录和差异记录并通过金额、笔数复核后才可确认；
- `CONFIRMED` 只表示平台侧财务确认，不表示 ERP 已入账或加盟商已收款；
- 一期结算只生成复核明细和批次，不执行付款。

## 7. 核心状态定义

### 7.1 活动状态

```text
DRAFT → PENDING_APPROVAL → SCHEDULED → ACTIVE → ENDED
                         ↘ REJECTED
ACTIVE → TERMINATED
```

### 7.2 领取申请状态

```text
PROCESSING → SUCCESS
PROCESSING → COMPENSATING → FAILED
```

对外可将 `COMPENSATING` 继续显示为“结果确认中”，避免库存尚未恢复时诱导用户立即重试。

### 7.3 用户权益状态

```text
AVAILABLE → USED
AVAILABLE → EXPIRED
AVAILABLE → CANCELLED
USED → AVAILABLE     仅限满足撤销恢复规则
USED → EXPIRED       撤销时权益已经过期
```

### 7.4 核销和结算状态

```text
核销：PROCESSING → SUCCESS → REVERSED
                ↘ FAILED

对账：UNRECONCILED → MATCHED
                    ↘ DIFFERENCE

结算明细：PENDING_CONFIRM → CONFIRMED
结算批次：DRAFT → PENDING_CONFIRM → CONFIRMED
```

状态名称是设计输入，允许在详细设计阶段调整，但业务含义不能被合并丢失。

## 9. 一期业务验收条件

### 9.1 领取

- 同一会员重复提交不能重复占用库存或生成多份权益；
- 库存耗尽后不能继续成功领取；
- 请求受理、处理中、成功和失败可以查询；
- 最终成功时卡包存在可查询权益；
- 最终失败时库存和领取占位得到补偿并留下原因记录。

### 9.2 核销与撤销

- 相同 POS 请求重复提交不会重复核销；
- 同一权益并发核销最多一个成功；
- 响应丢失后可通过原请求号恢复首次结果；
- 当天合法撤销保留核销及撤销审计记录；
- 已过期或结算锁定场景按照冻结规则处理。

### 9.3 对账

- 相同批次文件重复导入不重复生成明细；
- 相同批次号但内容变化时阻断结算；
- 空文件表示明确的零交易，缺少文件不能被解释为零交易；
- 坏行或汇总不一致时批次不得自动进入结算；
- 差异记录能够按活动、门店、日期和流水号查询。

## 10. 非功能约束

- 所有性能数字必须通过新业务链路重新测试，不能沿用旧秒杀结果直接宣称；
- 金额统一使用人民币分保存和传输；
- 业务时间暂按北京时间，接口使用带时区的 ISO 8601 时间；
- 会员 Token、平台 Token、密钥、签名和完整券码不得写入普通日志；
- 生产凭证不得写入仓库；
- 外部调用需要区分业务失败、临时技术失败和结果未知；
- Mock 通过仅表示模拟契约成立，不代表完成真实厂商联调或生产上线。

3. 活动、权益模板、领取申请、权益、核销和结算的最终表结构；
4. 券码生成、展示和防截图滥用方案；
5. POS 凭证按门店还是终端分配；
6. 对账文件签名、加密和更正批次的最终格式；
7. 正式容量目标、SLA、告警阈值和数据保留期限。
