# 青禾茶饮项目简历与面试说明

> 这份材料只从仓库现有代码和验证证据生成。项目应标注为“个人工程化改造 / 模拟企业项目”，不能虚构真实甲方、团队人数、上线时间、生产流量或付款结果。

## 1. 推荐项目标题

**青禾茶饮会员营销平台｜个人工程化改造与业务闭环实践**

不建议再以“黑马点评 Plus”作为简历项目名。面试被问到来源时，应主动说明：最初从点评秒杀工程学习 Redis/MQ 基础，随后按照模拟连锁茶饮需求重建业务模型、契约、数据表和验证链路，旧代码与青禾代码保留清晰边界。

## 2. 简历项目简介

面向连锁茶饮总部营销和门店履约场景，独立完成优惠券权益模块的需求还原、接口契约、后端实现与本地系统验证，覆盖活动审批发布、会员异步领券、POS 幂等核销与撤销、T+1 对账及加盟补贴确认；采用模块化单体，在复用 Spring Boot、Redis、RabbitMQ、MySQL 技术基础的同时，将旧点评业务默认隔离。

## 3. 推荐四条项目要点

1. **重构业务模型**：将原秒杀下单语义拆分为 `ClaimRequest`、`MemberEntitlement`、`Redemption`、`SubsidyCandidate`、`ReconBatch` 和 `SettlementBatch` 等独立事实，落地活动审批、发布快照、直营/加盟补贴分流及财务整批确认状态机。
2. **实现可靠异步发券**：使用 Redis Lua 原子完成库存与一人一次预留，以 MySQL Transactional Outbox 连接业务事务和 RabbitMQ 至少一次投递，并通过租约、幂等消费、失败终态及补偿任务覆盖 DB/MQ/Redis 间的失败窗口。
3. **实现 POS 履约安全与幂等**：设计 HMAC-SHA256 签名、时间窗和 nonce 防重放；以稳定请求号和请求摘要支持重复核销返回首次结果、冲突识别和响应丢失后的原结果恢复，并验证同券并发最多一次成功。
4. **打通 T+1 对账与补贴闭环**：实现 manifest/CSV 校验、SHA-256 文件幂等、分块导入续跑和多类差异隔离；直营店只参与对账，加盟店一致记录才生成待确认补贴明细，支持结算批次校验、整批确认和脱敏导出。

如果版面允许，可增加第五条：

5. **建立可执行交付证据**：以 OpenAPI/JSON Schema、V001—V008 数据库迁移、Mock、真实 MySQL/Redis/RabbitMQ 集成测试和跨模块系统旅程逐阶段设 Gate；WP-10 完整回归 181 项全部通过，并将依赖审计剩余风险明确阻断为不可公网或生产部署。

## 5. 面试时最可能被追问

### 为什么不直接沿用“优惠券订单”？

领取请求可能已受理但尚未发券，所以申请和资产不能是同一个状态。`ClaimRequest` 解决异步受理、查询和失败补偿，`MemberEntitlement` 表达真正可用的券；只有后者创建且卡包可查，申请才进入 `SUCCESS`。

### Redis 扣成功、MySQL 写失败怎么办？

Redis 预留不是最终事实。申请落库失败后由幂等补偿归还库存和会员资格；补偿自身可重试并记录状态。运营端还能只读检查 Redis 孤儿预留，避免提供危险的通用改 Redis 接口。

### 为什么用了 Outbox，还要处理重复消息？

Outbox 解决 DB 提交和消息发送之间的原子性缺口，但常见消息链路仍是至少一次投递。Publisher 重试、确认丢失或消费者 ACK 丢失都可能重复，因此消费端还必须以 eventId、claimNo 和权益唯一约束幂等。

### POS 超时为什么不能换一个请求号重试？

超时不代表服务器没成功。换请求号可能把一次履约变成两次。POS 应先按原 `posRequestNo` 查询；仍未找到时，也只能用原编号和原内容重提。相同编号但摘要不同必须返回冲突。

### 直营店和加盟店为什么处理不同？

两者都要产生核销并参加 T+1 对账，但直营成本由总部内部承担，不形成加盟补贴候选；加盟门店替总部履约，成功核销时需在同一事务中冻结活动发布时的补贴快照，等待对账一致后再进入财务确认。

### 为什么结算确认不等于付款？

本模块只负责生成可核对明细、阻断差异和记录财务确认。ERP 入账、资金支付和加盟商到账属于外部流程；如果把 `CONFIRMED` 命名成 `PAID`，系统就会表达一个自己无法证明的事实。

### 为什么没有拆微服务？

一期业务量和团队边界都是模拟，没有证据证明独立部署收益能覆盖分布式事务、运维和联调成本。模块化单体已经通过包边界、独立领域模型、接口契约和适配器隔离职责，未来只有出现真实组织或容量边界再拆分。

### 181 个测试是不是说明能上线？

不能。它只说明本地定义的主旅程、失败、并发、安全和迁移场景通过。真实上线仍缺厂商联调、生产容量、长稳、渗透、灰度、灾备和受支持的框架版本；依赖审计甚至明确把公网和生产部署列为阻断项。

7. Git 的 WP 分支与中文小提交：说明开发过程可追溯。

- “对接了真实 POS、会员中心、SFTP、ERP”——当前均为 Mock 或本地适配器；
- “生产 QPS/P95/P99”——只有本机回归样本；

- “系统已达到生产级安全”——旧框架依赖风险尚未清零；
- “从零开发全部系统”——仓库确实继承了旧点评工程基础。
