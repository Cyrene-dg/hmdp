## 2. 估时口径与前提

### 2.1 口径

- `1 PD` 表示一名熟悉 Java/Spring 的开发者一个专注工作日；
- 区间包含编码、自动化测试、局部文档和自检，不包含长期等待外部人员回复的日历时间；
- 估时面向“复用现有工程基础并重构核心领域”，不是从零建设完整茶饮点单、供应链、支付和 ERP；
- 当前由一名后端开发者主导，兼职学习或边做边补知识时，日历周期会明显长于人日总和；
- 原始区间之外另保留 15%—25% 风险储备，用于旧依赖兼容、并发缺陷、契约调整和返工；
- 未经实际任务记录，不把估时写成“实际投入”或“团队规模”。

### 2.2 已知前提

- 复用现有 Spring Boot、MySQL、Redis、RabbitMQ 和基础工程结构；
- 新业务代码进入 `com.qinghe.marketing`，与 `com.hmdp` 渐进共存；
- 外部会员中心、POS 和对账文件均先用 Mock/模拟契约；
- 一期只覆盖免费领取型权益、试点门店核销、当天撤销、T+1 对账和财务确认前明细；
- 管理后台以 API 和必要查询为主，不在本期重做完整前端；
- 不开发真实支付、点单、库存供应链、ERP 自动付款和全国门店推广。

## 3. 优先级与完成规则

| 标记 | 含义 | 规则 |
|---|---|---|
| P0 | 架构或主链路阻断项 | 不完成不得继续依赖它的工作包 |
| P1 | 一期闭环必需 | 试点演示和端到端验收前必须完成 |
| P2 | 生产化证据和可维护性 | 进入最终项目包装前完成，可随主链路并行 |
| Gate | 阶段门槛 | 需要可复查的代码、测试、日志或报告，不接受口头“应该可以” |

单个工作包只有同时满足以下条件才可标记 `DONE`：

- 代码已提交且范围与设计一致；
- 自动化测试覆盖该包主要成功、重复和失败路径；
- 涉及状态或接口时，契约和状态文档同步更新；
- 没有把未验证性能、真实厂商联调或生产上线写成完成；
- 能给下一工作包提供稳定输入。

## 5. 工作包明细

### WP-00 Mock 与契约测试骨架（2—3 PD）

**目标：** 在写领域主链路前，先证明双方对请求号、状态和错误语义理解一致。

**任务：**

- 为会员中心和 POS 模拟契约建立可启动的 Mock；
- 在测试中解析两份 OpenAPI YAML，校验关键路径和 schema；
- 优先执行 P0：相同请求返回首次结果、请求摘要冲突、超时后查询、同券并发只成功一次的测试骨架；
- 固定响应丢失恢复规则：短间隔查询，仍 `NOT_FOUND` 时使用原 `posRequestNo` 和原请求内容重提；
- 为对账 CSV 建立最小 fixture 和 schema 校验入口。

**完成标准：** Mock 可重复启动；OpenAPI 与 CSV fixture 校验通过；P0 测试骨架可运行并明确标注尚未实现的业务行为。此阶段不要求 POS 核销、响应丢失和同券并发等尚无实现的用例通过；它们在 WP-06 后执行，并在 WP-10 组合验证。当前 32 项 PoC 均为 `NOT_RUN`，执行后逐项回填。

**当前结果：** `DONE`。会员中心 Mock、POS 模拟客户端、平台 OpenAPI、manifest schema 和四组文件 fixture 已建立；17 项基础设施断言通过，5 项 POS 业务行为骨架明确跳过。证据见 [WP-00 契约基础设施验证记录](../contracts/WP00_契约基础设施验证记录_v1.0.md)。

### WP-01 新领域工程与数据骨架（3—5 PD）

**目标：** 建立不依赖旧点评业务服务的新边界。

**任务：**

- 新建 `com.qinghe.marketing` 根包和模块目录；
- 配置应用同时扫描新旧包，但禁止新模块依赖旧 Controller/Service；
- 引入可回滚、可审查的 `qh_` 增量迁移脚本；
- 建立业务编号、统一错误码、时钟、traceId、金额和操作审计公共组件；
- 建立测试容器或等效的 MySQL、Redis、RabbitMQ 集成测试环境。

**完成标准：** 空的新模块可启动；迁移可在干净库执行；最小回滚/前向兼容策略有测试；架构依赖检查能发现禁止依赖。

**当前结果：** `DONE`。已建立 `com.qinghe.marketing` 模块边界、18 张 `qh_` 核心表迁移和回滚、业务编号/时钟/金额/traceId/审计公共件以及架构依赖门禁；青禾隔离上下文不会启动旧 RabbitMQ 消费者。10 项非数据库门禁、1 项真实 MySQL 临时库迁移回滚均通过，且无残留 `qh_wp01_*` 数据库。证据见 [WP-01 开发检查点](./WP01_开发检查点_2026-09-08.md)。

### WP-02 身份与门店适配（3—5 PD）

**目标：** 提供领取和 POS 所需的稳定会员、门店身份。

**任务：**

- 实现会员中心 Token 校验适配器和短期平台会话；
- 建立外部会员号与平台会员 ID 映射；
- 实现门店版本化导入、校验、冲突报告和停用处理；
- 按门店建立 POS ClientId/密钥引用，密钥不入库明文和普通日志；
- 分离会员、管理、POS 三条认证链。

**完成标准：** Mock 会员冻结、超时、限流有稳定处理；重复门店文件不重复导入；停用门店不能核销；越权和签名失败有测试。

**当前结果：** `DONE`。已完成会员中心 Token 适配、短期平台会话与会员映射、MySQL 权威会话和 Redis 加速、版本化门店导入、POS 密钥引用与轮换，以及会员/管理/POS 三条认证边界。停用门店已在 POS 认证入口拒绝；真正的验券与核销事实仍属于 WP-06，当前不提前宣称完成。68 项 WP-00—WP-02/遗留回归中 63 项通过、5 项 WP-06 行为骨架按计划跳过，另有 1 项真实 MySQL 迁移回滚集成测试通过。证据见 [WP-02 开发检查点](./WP02_开发检查点_2026-09-09.md)。

### WP-03 活动与库存基线（4—6 PD）

**目标：** 冻结发券所需的规则、门店和库存事实。

**任务：**

- 实现 BenefitTemplate、Campaign、CampaignStore、CampaignInventory；
- 支持草稿、提交、审核、发布、终止的合法状态迁移；
- 发布时冻结权益规则、适用门店、补贴金额和活动总库存；
- 同一活动的加盟门店使用同一单张补贴；直营补贴为 0；
- SCHEDULED/ACTIVE 只允许通过独立审批记录追加库存，不覆盖初始总量且不得减少；
- 不在活动单行逐次维护 `issued_count`；成功量由权益事实聚合；
- 初始化 Redis 可预留库存，并提供 MySQL/Redis 核对入口。

**完成标准：** 发布后核心规则不能覆盖修改；库存只能由合规调整单增加且一单只生效一次；无适用门店或非法状态不能发布；重复发布幂等。

**当前结果：** `DONE`。已实现权益模板、活动草稿与审核发布、不可变发布快照、适用门店与直营/加盟补贴快照、库存调整审批、Redis 可用库存初始化及 MySQL/Redis 核对入口。完整 WP-00—WP-03 回归 89 项中 84 项通过、5 项 WP-06 行为骨架按计划跳过；真实 MySQL 与 Redis 集成探针各 1 项通过。证据见 [WP-03 开发检查点](./WP03_开发检查点_2026-09-09.md)。

### WP-04 领取受理与 Outbox（6—9 PD）

**目标：** 完成“请求受理”，但不把受理误认为发券成功。

**任务：**

- 重写 Lua：活动窗口、库存预留、每活动每会员一次、请求与 reservationId；
- Redis 预留成功后，本地事务写 `ClaimRequest(PROCESSING)` 与 `OutboxEvent(NEW)`；
- DB 失败时请求线程尝试幂等补偿，预留扫描负责崩溃兜底；
- Outbox 多实例租约、重试、`DEAD` 和投递审计；Publisher ACK 只代表发送；
- 建立领取接口与结果查询接口的请求幂等和摘要冲突规则；
- 完成新领取链路同步写申请与 Outbox 的容量测试。

**完成标准：** 任一预留最终能关联有效申请或被补偿；重复请求不重复扣库存；ACK 不改变权益结果；压测记录包含环境、数据规模、P95/P99 和错误率。

**当前结果：** `DONE`。已完成活动窗口内 Redis Lua 原子预留、请求摘要冲突识别、每活动每会员占位、ClaimRequest/Outbox 同事务受理、请求线程即时补偿与孤儿预留扫描、多实例 Outbox 租约、Publisher ACK/退回处理、指数退避、`DEAD` 状态和投递审计。会员领取与结果查询 API 已按契约实现；三轮本机核心受理容量样本共 900 次正式请求、0 错误，结果和限制见 [WP-04 领取受理容量基线](./WP04_领取受理容量基线_2026-09-09.md)。完整证据见 [WP-04 开发检查点](./WP04_开发检查点_2026-09-09.md)。

### WP-05 发券与卡包闭环（6—9 PD）

**目标：** 将 PROCESSING 申请可靠转为成功权益或已补偿失败。

**任务：**

- 按至少一次投递实现发券消费者；
- 本地事务创建 MemberEntitlement 并将 ClaimRequest 置为 SUCCESS；
- 用申请状态门闩、eventId/claimNo 幂等和唯一约束实现业务一次生效；
- Outbox `DEAD` 与 DLQ 重试耗尽进入统一失败处理器；
- 实现 `PROCESSING→COMPENSATING→FAILED` 和长期 COMPENSATING 扫描；
- 实现卡包列表、详情和券码保护策略。

**完成标准：** 重复、迟到、消费中崩溃不会重复发券；SUCCESS 必有权益；FAILED 必已补偿；卡包可查询最终事实。

**当前结果：** `DONE`。已完成至少一次消费、申请状态门闩、事件与申请归属校验、权益唯一落库与申请成功同事务、Outbox DEAD/DLQ 统一失败处理、`PROCESSING→COMPENSATING→FAILED`、长期补偿扫描、版本化死信/停车队列、卡包列表和详情、AES-GCM 券码加密与掩码展示、幂等到期任务。真实 MySQL、Redis、RabbitMQ 探针及完整青禾门禁通过，详见 [WP-05 开发检查点](./WP05_开发检查点_2026-09-09.md)。

### WP-06 POS 验券与核销（5—8 PD）

**目标：** 完成门店可恢复、可审计的一次核销。

**任务：**

- HMAC 签名、时间窗、nonce、防重放和按门店凭证；
- 验券只读，不锁券；
- 核销事务条件更新权益、写 Redemption 和 SubsidyCandidate(UNRECONCILED)；
- 只有加盟店创建 SubsidyCandidate；直营店仍参与核销与 T+1 对账但不产生补贴候选；
- 相同请求号同摘要返回首次结果，不同摘要返回 `REQUEST_CONFLICT`；
- 实现按原请求号查询首次结果；
- 配置领取与 POS 独立限流、线程池和指标，执行活动峰值下 POS 保护测试。

**完成标准：** 同券并发最多一个成功；响应丢失可恢复原结果；新请求号不能冒充原请求恢复；领取过载时 POS 仍满足经测试确认的基线。

**当前结果：** `DONE`。已实现 POS HMAC 时间窗与 nonce 防重放、只读验券、核销请求摘要幂等、权益行锁与版本门闩、Redemption 落库、直营/加盟补贴候选分流和原请求结果查询；领取与 POS 使用独立有界线程池、准入上限和指标。5 项原 POS 行为骨架已转为可执行测试；完整门禁 143 项全部通过，包含真实 MySQL V001—V006 正反迁移、同券并发最多一次成功和本地领取饱和时 POS 独立容量验证。详见 [WP-06 开发检查点](./WP06_开发检查点_2026-09-10.md)。该结果仍是本地模拟实现，不代表真实 POS 联调。

### WP-07 撤销与结算锁（3—5 PD）

**目标：** 不删除原核销，按规则恢复权益并取消未锁定候选。

**任务：**

- 实现撤销请求幂等和原核销引用；
- 校验原门店、当天、未结算锁定和权益有效期；
- 写独立 RedemptionReversal，原核销转 REVERSED；
- 未确认候选及已生成的待确认结算明细转 CANCELLED；权益转 AVAILABLE 或 EXPIRED；
- 跨日或锁定后拒绝自动撤销并进入差异处理。

**完成标准：** 原核销记录始终保留；重复撤销返回首次结果；不能因撤销恢复已过期权益或覆盖已确认结算。

**当前结果：** `DONE`。已实现 POS-04 HMAC 接口、撤销请求摘要幂等、原门店/原单/北京时间当天校验、原 Redemption 保留并转 `REVERSED`、权益按撤销时有效期恢复 `AVAILABLE` 或转 `EXPIRED`、加盟候选和待确认明细取消、待确认批次回到 `DRAFT` 重建，以及 `CONFIRMED` 明细/批次结算锁保护。失败请求写入独立恢复记录供人工差异处理；真实 MySQL V001—V007 正反迁移和完整 151 项门禁通过。详见 [WP-07 开发检查点](./WP07_开发检查点_2026-09-10.md)。该结果仍是本地模拟实现，不代表真实 POS 联调。

### WP-08 T+1 对账与结算明细（6—9 PD）

**目标：** 将平台核销和 POS 外部流水核对后，生成可供财务确认的明细。

**任务：**

- 实现文件发现、checksum、批次唯一、归档和错误文件隔离；
- 分块导入 ReconRecord，记录进度并支持续跑；
- 按核销号/POS 请求号匹配，输出一致、缺失、金额差异、状态差异；
- 整批校验完成前不生成可确认结算；
- 一致候选转 MATCHED，并生成 SettlementDetail(PENDING_CONFIRM)；
- 差异、直营和已取消记录排除后，有合格加盟明细才生成 SettlementBatch，财务按批确认；
- 财务确认后批次与明细转 CONFIRMED，导出只表达待处理/已确认，不表达真实付款；
- 更正通过新批次，不覆盖原批次和原始行摘要。

**完成标准：** 同一文件不重复结算；同批次不同内容阻断；部分坏行可定位和续跑；差异未关闭不能混入正常导出。

**当前结果：** `DONE`。已实现受控目录文件发现与隔离、manifest/CSV 严格校验、`provider + batchNo` 幂等和 checksum 冲突阻断、分块导入续跑、平台事实匹配与差异分类、直营/加盟分流、待确认明细、结算批次生成/确认/导出及操作审计。真实 MySQL V001—V008 正反迁移和完整 166 项青禾门禁通过。详见 [WP-08 开发检查点](./WP08_开发检查点_2026-09-10.md)。该结果仍是本地模拟实现，不代表真实 SFTP/POS 联调、真实付款或生产上线。

## 8. 时间不足时如何裁剪

为了守住“复用现有工程，不重做完整系统”的边界，时间不足时按下列顺序裁剪：

**可以后移：**

- 完整管理端页面，保留 API、脚本或最小查询入口；
- 多种复杂券型，先完成一种免费领取权益；
- 自动告警通知渠道，先有指标和可执行排查手册；
- 自动 ERP 入账、真实付款、全国门店推广；
- Maven 坐标和全部旧包的一次性改名。

**不能裁掉：**

- 领取申请与权益分离；
- Publisher ACK 不等于发券成功；
- 失败补偿、迟到消息和孤儿预留处理；
- POS 原请求号查询与恢复；
- 同券并发核销保护；
- 补贴候选与结算明细分离；
- 对账批次幂等、冲突阻断和差异留痕；
- 未验证能力不得进入简历成果。
