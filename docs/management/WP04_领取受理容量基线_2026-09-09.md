# WP-04 领取受理容量基线（2026-09-09）

> 结论性质：本机模拟依赖基线，不代表生产容量、真实会员中心/POS 联调结果或 SLA 承诺。

## 1. 验证目标

验证新领取链路中最有争议的同步路径，而不是复用旧点评秒杀数字：

```text
Redis Lua 原子预留
→ MySQL 本地事务写 ClaimRequest(PROCESSING)
→ 同一事务写 OutboxEvent(NEW)
→ Redis 预留标记改为 PERSISTED
```

本次不包含 HTTP 网关、会员中心调用、RabbitMQ 消费发券和前端轮询，因此结果只能作为 WP-04 核心受理路径的开发机基线。

## 2. 环境与数据

| 项目 | 本次环境 |
|---|---|
| 操作系统 | Windows NT 10.0.26200.0 |
| CPU | 13th Gen Intel Core i7-13700H，JVM 可见 20 个处理器 |
| 内存 | 约 23.8 GB |
| Java | 17.0.18（工程目标字节码仍为 Java 8） |
| MySQL | 8.0.41，本机临时数据库，Hikari 最大连接数 16 |
| Redis | 5.0.14.1，本机单节点 |
| 并发数 | 16 |
| 预热 | 每轮 20 次，不计入样本 |
| 正式样本 | 每轮 300 次，共 3 轮 |
| 数据模型 | 每次使用不同会员、同一活动、每会员限领一次 |

每轮使用独立的随机 `qh_wp04_cap_*` 临时数据库和随机活动 Redis Key；运行结束后精确删除本轮 Redis Key 并删除临时数据库。

## 3. 结果

| 轮次 | 成功/总数 | 错误 | 吞吐量 req/s | P50 ms | P95 ms | P99 ms | Max ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1（冷启动影响较明显） | 300/300 | 0 | 844.23 | 16.67 | 27.65 | 84.74 | 147.28 |
| 2 | 300/300 | 0 | 1480.86 | 9.71 | 18.92 | 23.01 | 24.26 |
| 3 | 300/300 | 0 | 1406.85 | 8.76 | 27.97 | 43.43 | 45.87 |
| 三轮指标中位数 | 300/300 | 0 | 1406.85 | 9.71 | 27.65 | 43.43 | 45.87 |

三轮合计 900 个正式样本全部成功；每轮结束时均验证：

- Redis 活动可用库存由 320 归零；
- MySQL 中存在 320 条 ClaimRequest 和 320 条 OutboxEvent（含 20 条预热）；
- ClaimRequest 状态为 `PROCESSING`，Outbox 状态为 `NEW`；
- 没有因为 Outbox 的存在把申请提前标为 `SUCCESS`。

## 4. 当前判断

在这台开发机、单节点本机 MySQL/Redis、16 并发和小数据量条件下，同步写 ClaimRequest + Outbox 没有出现功能性失败，暂不需要为了假设的性能问题改成“只写 Redis、不落申请事实”的高风险方案。

首轮与后两轮差异明显，说明 JVM、连接池和数据库缓存预热对结果有影响。当前证据适合支持“现有设计可继续进入 WP-05”，不适合写成生产吞吐或面试中的线上峰值。

## 5. 局限与后续复测

- 数据量只有数百条，尚未覆盖大表索引、历史数据和长期运行抖动；
- MySQL、Redis 与应用位于同一台机器，网络延迟远低于生产部署；
- 没有包含会员身份交换、HTTP 序列化、限流、RabbitMQ Broker 与消费者；
- 没有包含 Redis 主从切换、数据库故障和进程崩溃；
- 当前只测“不同会员并发”，同一会员并发幂等由 Redis 真机 Gate 单独验证；
- WP-10 仍需在完整领取闭环下重做分层并发与故障测试。
