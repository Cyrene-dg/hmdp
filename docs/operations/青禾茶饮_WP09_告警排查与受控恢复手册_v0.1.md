# 青禾茶饮 WP-09 告警排查与受控恢复手册 v0.1

## 1. 使用边界

本文只描述当前仓库可验证的本地模拟能力，不代表真实监控平台、真实值班制度或生产 SLA。正式阈值、通知渠道、责任人姓名和数据保留期仍需在真实部署环境确认。

本地默认时间条件来自配置：

- 领取异常：`qinghe.operations.stuck-seconds`，默认 300 秒；
- Redis 孤儿预留：`qinghe.claim.recovery.orphan-seconds`，默认 120 秒；
- 待确认结算异常：`qinghe.operations.settlement-pending-seconds`，默认 86400 秒。

这些数值是故障演练触发条件，不是生产承诺。

## 2. 统一排查入口

所有入口要求管理端 `operation:read` 权限：

| 入口 | 用途 |
|---|---|
| `GET /api/v1/admin/operations/metrics` | 查看领取、POS、对账进程计数和 MySQL 当前积压快照 |
| `GET /api/v1/admin/exceptions` | 按 `exceptionType`、`status` 分页查看持久异常 |
| `GET /api/v1/admin/exceptions/redis-orphan-reservations?campaignId={id}&limit=100` | 有界检查指定活动的 Redis 孤儿预留 |
| `GET /api/v1/admin/business-traces?identifierType={type}&identifierValue={value}` | 用业务编号还原申请、消息、权益、核销、对账和结算时间线 |

不得用手机号、完整 Token、明文券码或密钥作为排查参数，也不得把这些值复制到日志或工单。

## 3. 高优先级故障卡

| 条件 | 责任角色（模拟） | 首个排查入口 | 允许的恢复动作 | 禁止动作 |
|---|---|---|---|---|
| `CLAIM_PROCESSING_STUCK` | 运营技术支持 | 异常项的 `claimNo` → 业务链路 | 检查 Outbox 状态与消息依赖；恢复依赖后等待既有发布/消费任务按原事件继续 | 直接把申请改为 SUCCESS |
| `CLAIM_COMPENSATING_STUCK` | 运营技术支持 | `claimNo` → 业务链路 | 检查 Redis 可用性；恢复后让既有补偿恢复任务继续 | 手工回库存后再放任任务重复补偿 |
| `REDIS_ORPHAN_RESERVATION` | 运营技术支持 | 指定 `campaignId` 的孤儿检查 | 确认无 ClaimRequest 后，由既有孤儿恢复任务执行幂等补偿 | 删除 Redis 键或直接改库存 |
| `OUTBOX_DEAD` / `CLAIM_DLQ_FAILED` | 应用支持 | `eventId` → 业务链路 | 修复消息依赖并保留失败事实；当前版本没有通用重放按钮，需在评审后的专用恢复流程中处理 | 改 Outbox 为 PUBLISHED、换 eventId 重发 |
| `RECON_BATCH_FAILURE` / `RECON_FILE_MISSING` | 对账运营 | `reconBatchNo` → 批次详情 | 文件补齐或临时依赖恢复后，调用受控 `POST /api/v1/admin/recon-batches/{reconBatchNo}/retry` | 覆盖原文件、伪造零交易文件 |
| `RECON_DIFFERENCE` | 对账运营、财务复核 | `reconBatchNo` → 差异和链路 | 保持冻结，要求更正批次或人工复核；不直接生成结算 | 删除差异或修改原核销 |
| `SETTLEMENT_PENDING_STALE` | 财务复核 | `settlementBatchNo` → 批次与导出 | 对照导出明细复核；确认时调用受版本门闩保护的确认接口 | 改明细金额、把 CONFIRMED 当作已付款 |

## 4. 受控操作原则

1. 查询人员只有 `operation:read`，不能直接发券、核销、撤销或确认结算。
2. 对账重试使用 `recon:operate`；财务确认使用 `settlement:confirm`，不得共享高权限账号。
3. 已实现的对账重试、结算生成和确认会写操作日志，保留操作者、原因、前后状态、业务编号、请求号和 traceId。
4. `TRACE_ONLY` 表示当前没有安全的人工修改入口。没有入口是明确保护，不应使用 SQL 绕过。
5. 任何响应未知的 POS 请求必须以原 `posRequestNo` 查询首次结果，不能换号盲目重试。
