# 青禾茶饮 WP-10 发布与回滚演练手册 v0.1

> 适用范围：本地模拟试点演练。  
> 不适用范围：真实客户生产发布、真实 POS/SFTP/会员中心切换和真实付款。真实环境必须由双方 IT、DBA、运维、安全和业务负责人重新确认。

## 1. 发布原则

- 优先做功能开关回退和流量回退，不把删表作为常规回滚；
- 发布前保留数据库备份、应用制品、配置版本和迁移校验记录；
- 队列不执行 `purge`，不删除未知消息来制造“已排空”；
- ClaimRequest、Entitlement、Redemption、Reversal、Reconciliation 和 Settlement 都是业务事实，不直接改表伪造终态；
- 任何恢复动作必须使用原业务编号、幂等服务和操作审计；
- V/R 脚本的逆序测试只证明空的一次性数据库可回退，不自动授权对已有业务数据删表。

## 2. 发布前检查

### 2.1 代码与制品

```powershell
git status --short --branch
git rev-parse HEAD
mvn -DskipTests package
```

要求：工作区干净；HEAD 对应已通过 Gate 的 WP 提交；构建成功；未跟踪配置、凭据和扫描原始报告不进入制品。

### 2.2 配置与密钥

逐项确认但不打印明文：

- MySQL URL、用户、密码；
- Redis host、port、database、password；
- RabbitMQ host、port、vhost、user、password；
- POS `secretReference` 对应的外部密钥；
- 权益券码 AES-GCM key；
- 会员中心地址、超时和签名参数；
- `qinghe.claim.consumer.enabled`、Outbox Publisher、恢复调度和对账调度开关；
- 青禾与旧点评入口隔离配置。

### 2.3 数据库迁移

在一次性数据库先执行：

```text
V001 -> V002 -> V003 -> V004 -> V005 -> V006 -> V007 -> V008
```

验证：33 张 `qh_` 表存在，唯一键、外键和关键索引建立；随后在另一个空的一次性数据库演练 `R008 -> ... -> R001`，不能对真实业务库直接照搬逆序删除。

### 2.4 未终态数据检查

以下 SQL 为只读检查，表名与状态来自当前 V001—V008：

```sql
SELECT status, COUNT(*) FROM qh_claim_request
WHERE status IN ('PROCESSING','COMPENSATING') GROUP BY status;

SELECT status, COUNT(*) FROM qh_outbox_event
WHERE status IN ('NEW','RETRY','PUBLISHING','DEAD') GROUP BY status;

SELECT status, COUNT(*) FROM qh_pos_redemption_request
WHERE status='PROCESSING' GROUP BY status;

SELECT status, COUNT(*) FROM qh_pos_reversal_request
WHERE status='PROCESSING' GROUP BY status;

SELECT status, COUNT(*) FROM qh_recon_batch
WHERE status IN ('RECEIVED','IMPORTING','MATCHING','PARTIAL_FAILED','FAILED')
GROUP BY status;

SELECT status, COUNT(*), COALESCE(SUM(total_fen),0) FROM qh_settlement_batch
WHERE status IN ('DRAFT','PENDING_CONFIRM') GROUP BY status;
```

判定：

- `PROCESSING/COMPENSATING/PUBLISHING/IMPORTING/MATCHING` 必须明确是正在工作还是已超时；
- `DEAD/PARTIAL_FAILED/FAILED` 必须进入异常清单，不可忽略；
- `PENDING_CONFIRM` 不阻止只读发布，但禁止在未知版本上自动确认；
- 有未终态并不等于必须改表，先用 WP-09 业务链路和异常查询定位。

## 3. 队列排空演练

涉及队列：

```text
qinghe.claim.issue.v1.queue
qinghe.claim.issue.v1.dead.queue
qinghe.claim.issue.v1.parking.queue
```

步骤：

1. 先关闭新的领取流量或关闭领取入口，不先停消费者；
2. 保持主队列消费者运行，观察主队列 ready/unacked 下降；
3. 同时查询 `qh_outbox_event` 的 NEW、RETRY、PUBLISHING、DEAD；
4. 主队列为零后，确认没有持续产生新的 Outbox；
5. dead/parking 不做 purge，导出 eventId、claimNo、失败原因并通过业务链路查询；
6. 只对已判定可重试且仍满足状态门闩的事件使用既有恢复服务；
7. 结果未知时保持消息和数据库事实，升级处理，不手工伪造 ACK。

通过条件：主队列无待处理/未确认消息；Outbox 无无主 PUBLISHING；dead/parking 每条都有处置决定；ClaimRequest 与 Entitlement 可按编号核对。

## 4. 发布顺序

```text
备份与只读检查
  -> 应用先以消费者/调度关闭状态部署
  -> 执行增量迁移 V001—V008 中尚未应用部分
  -> 启动应用并检查健康、日志和数据库连接
  -> 打开只读管理查询
  -> 打开发券消费者与恢复调度
  -> 小流量开放领取/POS
  -> 验证完整业务编号时间线
  -> 最后打开对账文件调度
```

本地演练最小验证：创建活动、领取、发券、卡包查询、加盟核销、对账、结算确认与脱敏导出；另以独立用例验证撤销和 RabbitMQ DLQ。

## 5. 观察窗口

重点观察：

- Claim `PROCESSING/COMPENSATING` 是否持续增长；
- Outbox `RETRY/DEAD` 和 PUBLISHING 租约是否回收；
- 主/dead/parking 队列深度；
- POS accepted/rejected/succeeded/failed 和结果未知比例；
- Redis 库存、会员占位和 MySQL ClaimRequest 是否可核对；
- 对账 MISSING、坏行、差异、失败和 PENDING_CONFIRM 金额；
- 日志中是否出现凭据、完整券码、签名和 Token。

当前项目没有真实 Prometheus/Grafana 或生产阈值；本地指标仅辅助演练，不能伪造生产告警结论。

## 6. 回滚决策

### 6.1 应用发布失败、尚无新版本业务写入

- 关闭入口、消费者和调度；
- 回退到上一制品和配置；
- 若数据库仅新增空表且经 DBA 确认，可在备份后按 R008→R001 的适用范围回退；
- 重新执行上一版本 smoke test。

### 6.2 已产生 Claim/Entitlement/Redemption 等新事实

- 不执行删表回滚；
- 关闭新入口，保留查询与消费者，先排空或冻结消息；
- 回退应用前确认旧版本能否识别现有 schema 与状态；
- 若不兼容，采用向前修复或兼容版本，不删除业务事实；
- 对异常事实走补偿、撤销、更正批次或人工差异流程。

### 6.3 已有 CONFIRMED 结算

- 禁止删除、覆盖或重新生成已确认批次；
- 禁止通过业务撤销偷偷改动已确认金额；
- 记录差异并进入独立调整/冲正需求；当前一期没有实现付款后调账。

### 6.4 消息积压或消费者故障

- 停止新增领取，保留数据库和队列现场；
- 检查 Outbox、主队列、dead、parking 和 ClaimRequest 状态；
- 恢复消费者后依靠 eventId/claimNo 幂等处理；
- 不 purge、不换业务号、不直接把 Claim 改成 SUCCESS。

## 7. 恢复后核验

```sql
SELECT status, COUNT(*) FROM qh_claim_request GROUP BY status;
SELECT status, COUNT(*) FROM qh_outbox_event GROUP BY status;
SELECT status, COUNT(*) FROM qh_member_entitlement GROUP BY status;
SELECT status, COUNT(*) FROM qh_pos_redemption_request GROUP BY status;
SELECT status, COUNT(*) FROM qh_pos_reversal_request GROUP BY status;
SELECT status, COUNT(*) FROM qh_recon_batch GROUP BY status;
SELECT status, COUNT(*), COALESCE(SUM(total_fen),0)
FROM qh_settlement_batch GROUP BY status;
```

抽样选择 claimNo、eventId、entitlementNo、posRequestNo、redemptionNo、reconBatchNo、settlementBatchNo，通过 WP-09 `/api/v1/admin/business-traces` 还原时间线；检查卡包和结算导出不包含完整券码。
