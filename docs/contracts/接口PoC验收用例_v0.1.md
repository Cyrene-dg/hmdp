# 青禾茶饮接口 PoC 验收用例 v0.1

> 用途：在正式领域设计和业务开发前，用 Mock 验证接口契约是否能够处理成功、失败、超时、重复和结果未知  
> 当前状态：全部 `NOT_RUN`，本文件不是测试报告  
> 证据原则：只有实际执行并保存脱敏请求、响应、日志和断言后，才能改为 PASS 或 FAIL

## 1. PoC 边界

本轮只验证：

- 会员 Token 校验和平台短期会话的边界；
- POS 核销请求号、原结果查询和并发防重语义；
- 当天原单撤销的契约和状态限制；
- POS T+1 对账文件的批次幂等及异常阻断。

本轮不验证：

- 真实厂商网络和生产 SLA；
- 十万张权益活动的完整容量；
- 完整后台页面、财务付款和 ERP；
- 最终数据库表结构；
- 真实品牌或真实门店生产联调。

## 2. 状态定义

| 状态 | 含义 |
|---|---|
| NOT_RUN | 只有测试设计，尚未执行 |
| PASS | 按约定环境实际执行，所有断言通过并保存证据 |
| FAIL | 已执行但至少一个关键断言不成立 |
| BLOCKED | 因环境、依赖或前置数据缺失无法执行 |
| CONDITIONAL | 核心路径通过，但存在必须进入设计约束的限制 |

## 3. 会员中心契约用例

| 编号 | 场景 | 操作 | 预期结果 | 失败后处理 | 状态 |
|---|---|---|---|---|---|
| MEM-P01 | 有效 Token | Mock 返回 ACTIVE 会员 | 建立平台短期会话；只保存最小会员标识；领取时不再次调用会员中心 | 检查映射、会话 TTL 和响应解析 | NOT_RUN |
| MEM-P02 | 无效 Token | Mock 返回 401/TOKEN_INVALID | 不建立会话；返回登录失效；不重试同一 Token | 修正错误码映射，不能降级为信任前端 memberNo | NOT_RUN |
| MEM-P03 | 冻结会员 | Mock 返回 403/MEMBER_FROZEN | 不建立会话；记录脱敏业务失败 | 若被放行则视为 P0 失败 | NOT_RUN |
| MEM-P04 | 会员中心超时 | Mock 延迟超过调用超时 | 新登录失败或稍后重试；不得建立匿名可信会话 | 验证超时、熔断和降级策略 | NOT_RUN |
| MEM-P05 | 会员中心限流 | Mock 返回 429 和 Retry-After | 有限重试或向上游返回稍后再试；不得无限重试 | 调整退避和最大次数 | NOT_RUN |
| MEM-P06 | 已有平台会话 | 建立会话后让会员中心超时，再发起领取前置校验 | 领取身份解析不依赖本次外部调用 | 若仍调用会员中心，说明主链路未解耦 | NOT_RUN |
| MEM-P07 | Token 敏感信息 | 检查应用日志和异常日志 | 不出现完整 memberToken、平台 Token、签名和密钥 | 增加脱敏并重新执行 | NOT_RUN |

## 4. POS 核销契约用例

| 编号 | 场景 | 操作 | 预期结果 | 失败后处理 | 状态 |
|---|---|---|---|---|---|
| POS-P01 | 正常验券 | AVAILABLE 权益在适用门店验券 | 返回可用及权益摘要；权益状态不变化 | 修正验券与核销职责 | NOT_RUN |
| POS-P02 | 正常核销 | 使用唯一 posRequestNo 在加盟店核销 AVAILABLE 权益 | 返回 SUCCESS 和 redemptionNo；权益变为 USED；只有一条成功核销和一条加盟补贴候选 | 检查事务边界和条件更新 | NOT_RUN |
| POS-P03 | 相同请求重复提交 | 同一 posRequestNo 连续提交三次 | 三次返回相同首次结果；只有一条核销；加盟店最多一条补贴候选，直营店没有候选 | 修正请求幂等存储 | NOT_RUN |
| POS-P04 | 响应丢失后查询 | 平台完成核销但模拟客户端丢弃响应，再按原请求号查询 | 查询得到首次 SUCCESS 和相同 redemptionNo | 原结果不可恢复则阻塞试点 | NOT_RUN |
| POS-P05 | 同券不同请求并发 | 两个不同 posRequestNo 同时核销一张 AVAILABLE 权益 | 最多一个成功；另一个返回 ALREADY_REDEEMED 或等价稳定冲突 | 修正条件更新、锁或唯一约束 | NOT_RUN |
| POS-P06 | 同请求号内容变化 | 先用请求号 A 核销券 X，再用请求号 A 提交券 Y | 返回 REQUEST_CONFLICT，不复用第一次成功掩盖参数冲突 | 保存请求摘要用于冲突判断 | NOT_RUN |
| POS-P07 | 不适用门店 | 在未参与活动的门店验券或核销 | 返回 STORE_NOT_APPLICABLE，权益保持不变 | 检查活动门店快照 | NOT_RUN |
| POS-P08 | 权益过期 | 核销已过期权益 | 返回 RIGHT_EXPIRED，不生成成功核销 | 检查时间和时区 | NOT_RUN |
| POS-P09 | 签名错误或重放 | 使用错误签名，或重复时间戳和 nonce | 拒绝请求且不改变业务状态 | 修正验签与 nonce 存储 | NOT_RUN |
| POS-P10 | 平台处理超时 | 模拟核销接口返回 202/PROCESSING | POS 不创建新业务请求；使用原 posRequestNo 查询 | POS 模拟客户端行为不符则判定 FAIL | NOT_RUN |

## 5. 撤销契约用例

| 编号 | 场景 | 操作 | 预期结果 | 失败后处理 | 状态 |
|---|---|---|---|---|---|
| REV-P01 | 当天合法撤销 | 撤销当天、原单、未结算核销，权益仍有效 | 原核销标记 REVERSED；生成撤销流水；权益恢复 AVAILABLE；加盟候选及未确认明细取消 | 修正条件校验和事务边界 | NOT_RUN |
| REV-P02 | 重复撤销 | 相同撤销请求号提交两次 | 返回第一次结果；只有一条有效撤销流水 | 修正撤销幂等 | NOT_RUN |
| REV-P03 | 撤销时权益过期 | 核销后将业务时间推进到过期再撤销 | 核销可标记撤销，但权益为 EXPIRED，不恢复可用 | 修正权益状态计算 | NOT_RUN |
| REV-P04 | 结算已锁定 | 对已进入锁定批次的核销发起撤销 | 返回 SETTLEMENT_LOCKED；不修改原核销和结算金额 | 转人工差异流程 | NOT_RUN |
| REV-P05 | 跨日撤销 | 次日对原核销发起在线撤销 | 返回 REVERSAL_NOT_ALLOWED；不自动修改权益 | 保留为人工流程，不扩大一期范围 | NOT_RUN |
| REV-P06 | 非原门店撤销 | 另一门店对原核销发起撤销 | 拒绝且记录安全审计 | 修正门店身份关联 | NOT_RUN |

## 6. POS 对账文件用例

| 编号 | 场景 | 输入 | 预期结果 | 失败后处理 | 状态 |
|---|---|---|---|---|---|
| REC-P01 | 正常文件 | 唯一批次、合法字段和汇总 | 导入成功；直营一致记录完成核对，加盟一致记录进入待确认明细；差异进入异常清单 | 检查字段映射和匹配规则 | NOT_RUN |
| REC-P02 | 相同文件重复上传 | 相同批次号、相同校验值导入两次 | 第二次识别为重复；不重复生成结算明细 | 修正批次唯一约束 | NOT_RUN |
| REC-P03 | 同批次内容变化 | 相同批次号、不同校验值 | 标记批次冲突；冻结该业务日自动结算；不覆盖原文件 | 要求更正批次并告警 | NOT_RUN |
| REC-P04 | 零交易空文件 | 只有表头的合法文件 | 导入成功并明确记录零交易 | 修正空文件与缺失文件判断 | NOT_RUN |
| REC-P05 | 到期未收到文件 | 超过最终截止时间仍无文件 | 告警并保持 WAITING/MISSING；不得自动视为零交易 | 联系模拟 POS 补传 | NOT_RUN |
| REC-P06 | 部分坏行 | 合法文件中加入缺字段或错误时间的行 | 批次标记 PARTIAL_FAILED；不自动进入结算 | 输出错误明细，使用新更正批次 | NOT_RUN |
| REC-P07 | 文件汇总不一致 | CSV 数据行数与 manifest.rowCount 不符 | 整批失败并告警 | 修正厂商生成逻辑或文件传输完整性 | NOT_RUN |
| REC-P08 | 更正批次 | 新批次引用原批次并修复错误 | 保留原批次；建立更正关系；不直接覆盖历史导入 | 完善版本和审计记录 | NOT_RUN |
| REC-P09 | 撤销先于原核销到达 | 更正或迟到文件中撤销记录先到 | 不丢弃；进入待匹配，原核销到达后重新匹配 | 设计迟到数据窗口 | NOT_RUN |

## 7. 契约级通过门槛

进入正式领域设计前，至少满足：

1. YAML 可以被标准解析器读取；
2. Mock 能稳定复现正常、无效、限流、超时和处理中响应；
3. POS-P02 至 POS-P06 的幂等及结果恢复语义全部通过；
4. REV-P01 至 REV-P05 的状态限制全部通过；
5. REC-P01 至 REC-P06 的批次安全规则全部通过；
6. 日志脱敏用例通过；
7. 所有 CONDITIONAL 项已经转成明确设计约束；
8. 测试结果不被描述为真实厂商联调或生产验证。

任一 P0 用例失败时，不直接进入大规模业务开发。先修改契约、范围或模拟外部能力，再重新验证。

## 8. 预期证据

后续实际执行时，每个用例至少保存：

- 用例编号和执行时间；
- Mock 场景配置；
- 脱敏请求和响应；
- 自动化断言结果；
- 关键数据库或缓存状态快照；
- 是否通过及失败原因；
- 对契约、范围或设计造成的修改。

性能、并发和故障恢复结果必须注明环境、数据量、并发模型和统计口径。
