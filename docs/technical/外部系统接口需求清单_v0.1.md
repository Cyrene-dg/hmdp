# 青禾茶饮外部系统接口需求清单 v0.1

> 文档性质：后端提出的接口能力需求，不是甲方或厂商已经提供的 API 文档  
> 当前用途：向甲方 IT 说明“为了完成一期，我们需要哪些系统提供什么能力”  
> 重要说明：路径、字段、签名、错误码和时限均需接口提供方确认
> 后续设计：详细接口、示例、错误码和文件协议已经整理到[一期接口设计说明 v1.0](../contracts/青禾茶饮_一期接口设计说明_v1.0.md)；冲突时以该文档和完整 PRD 为准

## 1. 系统边界

| 系统 | 暂定责任 | 与本平台的关系 | 一期重要性 |
|---|---|---|---|
| 会员中心 | 保存甲方会员主档和会员有效状态 | 本平台查询或接收会员身份，不取代会员中心 | P0 |
| 微信小程序 | 展示活动、发起领取、展示卡包和结果 | 小程序调用本平台用户侧 API | P0 |
| 门店/POS | 门店验券、核销、查询和撤销 | POS 调用本平台履约 API；双方交换核销结果 | P0 |
| 门店主数据系统 | 维护门店编码、类型、状态和组织信息 | 本平台同步门店信息 | P0，可用试点清单临时代替 |
| 财务/ERP | 财务入账和实际付款 | 一期只接收本平台导出的结算明细，不做在线集成 | P1/一期外 |
| 消息通知平台 | 短信、模板消息或站内通知 | 发送领取结果、到期提醒等 | P2 |

## 2. 接口方向说明

```text
微信小程序 ──领取/查询──> 权益平台
会员中心   <──身份验证── 权益平台
门店主数据 <──门店同步── 权益平台
门店 POS   ──验券/核销/查询/撤销──> 权益平台
POS/数据平台 <──核销对账数据──> 权益平台
权益平台   ──结算文件──> 财务人员或 ERP
```

方向必须先说清，否则容易出现双方都在等对方开发同一个接口。

## 3. P0 接口能力清单

### 3.1 会员中心

| 编号 | 能力 | 调用方向 | 最少输入 | 最少输出 | 待确认点 |
|---|---|---|---|---|---|
| MEM-01 | 根据小程序登录态解析会员身份 | 权益平台 → 会员中心，或由小程序网关透传可信会员号 | 登录凭证或访问令牌 | 会员唯一编号、有效状态 | 令牌由谁校验、会员号是否稳定、接口超时时是否允许领取 |
| MEM-02 | 查询会员基础状态 | 权益平台 → 会员中心 | 会员编号 | 是否存在、是否冻结、会员等级（若一期使用） | 查询时限、缓存期限、冻结会员的已领券是否仍可核销 |

一期不需要复制完整会员资料。手机号、姓名等字段遵循最小化原则，非必要不存储。

### 3.2 门店主数据

| 编号 | 能力 | 调用方向 | 最少输入 | 最少输出 | 待确认点 |
|---|---|---|---|---|---|
| STORE-01 | 全量或分页取得门店清单 | 权益平台 → 门店系统，或甲方提供文件 | 分页参数/更新时间 | 门店编号、名称、直营加盟属性、状态、区域、POS版本 | 是否有接口；若无，一期文件由谁维护、多久更新一次 |
| STORE-02 | 增量同步门店变化 | 权益平台 → 门店系统，或门店系统推送 | 上次同步时间/版本号 | 新增、修改、停业记录 | 临时停业与永久闭店如何区分 |

试点期间可以由甲方提供十家门店的确认文件，但必须保留外部门店编号，不能只使用我方自增 ID 与 POS 对接。

### 3.3 POS 调用本平台

#### POS-01 验券

用途：店员收款前判断某张权益是否可以在当前门店使用，不改变权益状态。

最少请求信息：

- POS 请求号；
- 门店编号、终端编号；
- 券码；
- 请求时间；
- 签名或系统凭证。

最少响应信息：

- 是否可用；
- 权益名称和优惠内容；
- 失效时间；
- 不可用原因及稳定错误码；
- 平台响应流水号。

必须确认：验券结果可以缓存多久、验券成功后是否锁券、顾客换门店时如何处理。

#### POS-02 核销

用途：将可使用权益原子地变更为已使用并生成核销流水。

最少请求信息：

- 唯一核销请求号；
- 原 POS 交易号；
- 门店编号、终端编号、操作员编号；
- 券码；
- 核销时间；
- 商品或订单信息是否必传，待确认。

最少响应信息：

- 核销结果；
- 平台核销流水号；
- 权益最终状态；
- 首次核销时间；
- 失败或处理中错误码。

幂等要求：相同核销请求号重复调用必须返回第一次处理结果，不能生成第二笔核销。

#### POS-03 查询原核销结果

用途：POS 调用核销超时后，查询第一次请求是否成功。

查询键优先级：

1. 唯一核销请求号；
2. 平台核销流水号；
3. 原 POS 交易号加门店编号。

必须返回明确的 SUCCESS、FAILED、PROCESSING 或 NOT_FOUND，不能只返回“系统异常”。

#### POS-04 撤销核销

用途：试点阶段暂按“当天、原单、一次性撤销”提出能力需求。

最少请求信息：

- 唯一撤销请求号；
- 原核销请求号或平台核销流水号；
- 门店、操作员、撤销原因；
- 请求时间。

待甲方决定：

- 撤销后权益恢复为可用还是直接作废；
- 已进入财务结算批次后是否还能撤销；
- 跨日是否完全禁止，还是进入人工审批；
- POS 厂商是否实际支持撤销结果同步。

### 3.4 小程序调用本平台

| 编号 | 能力 | 最少输入 | 最少输出 | 关键语义 |
|---|---|---|---|---|
| MINI-01 | 查询可参与活动 | 会员身份、位置或门店（如需要） | 活动、时间、剩余状态、适用范围 | 不直接暴露敏感精确库存可由产品决定 |
| MINI-02 | 提交领取申请 | 活动编号、唯一请求号 | 领取申请号、ACCEPTED/PROCESSING/最终失败 | 接口受理不能伪装成权益已到账 |
| MINI-03 | 查询领取结果 | 领取申请号 | PROCESSING/SUCCESS/FAILED、权益编号、失败原因 | SUCCESS 必须表示卡包可查询 |
| MINI-04 | 查询用户卡包 | 状态、分页参数 | 可用/已用/过期权益摘要 | 数据归本平台还是旧券系统需要确认 |
| MINI-05 | 查询权益详情 | 权益编号 | 使用规则、适用门店、券码、有效期、状态 | 券码防枚举、防截图滥用策略待设计 |

## 4. 对账数据能力

对账数据的获取方式尚未确认，应要求甲方 IT 在以下方案中选择：

| 方案 | 描述 | 优点 | 风险 |
|---|---|---|---|
| A. POS 实时回传 | 每次核销和撤销实时通知平台 | 及时 | 网络超时和重复通知需要处理 |
| B. 平台主动查询 | 平台按时间或流水向 POS 查询 | 可主动补偿 | POS 必须提供稳定查询和分页能力 |
| C. 每日文件 | POS 每日提供核销及撤销文件 | 适合财务核对 | 时效较低，文件重复和缺失需管理 |
| D. 实时接口加每日文件 | 实时处理业务，每日文件作为对账依据 | 相对稳妥 | 实现和协调成本最高 |

项目组暂时建议 D，但这只是方案建议，必须根据 POS 厂商能力和项目预算决定。

对账数据至少需要：

- POS 交易号、核销请求号、平台核销流水号；
- 门店编号、终端编号；
- 券码或平台权益编号；
- 核销/撤销时间和当前状态；
- 原订单金额、优惠金额（如业务需要）；
- 数据生成时间和批次号。

## 5. 所有外部接口必须共同确认的事项

拿到 API 文档后，后端不能只看 URL 和 JSON 示例，还需要逐项确认：

1. 系统和业务负责人分别是谁；
2. 测试、预发布、生产地址及网络开通方式；
3. 鉴权、签名、时间戳、防重放和密钥轮换方式；
4. 请求唯一编号由谁生成，保存多久；
5. 连接超时、响应超时、限流阈值和可重试错误；
6. 重试是否保证幂等，重复请求返回什么；
7. 业务失败、系统失败、处理中和未知结果的错误码；
8. 原结果查询和数据补偿方式；
9. 字段长度、金额单位、时区、时间格式和字符编码；
10. 数据脱敏、日志保存和个人信息边界；
11. 接口版本升级及废弃通知期限；
12. 联调窗口、生产变更窗口和故障联系人。

## 6. 文档到达后的验证顺序

| 顺序 | 验证内容 | 为什么优先 |
|---:|---|---|
| 1 | 会员身份能否稳定解析 | 无法识别会员则领取链路不能开始 |
| 2 | POS 是否能调用我方验券和核销接口 | 决定门店履约能否成立 |
| 3 | 核销超时后是否有原结果查询 | 决定能否安全处理未知结果 |
| 4 | 撤销能力和状态同步 | 决定一期是否能承诺撤销 |
| 5 | POS 对账数据的获取方式 | 决定补贴结算闭环 |
| 6 | 门店数据同步 | 试点可临时用文件，全量前必须解决 |

每项验证应保存请求、响应、错误码、耗时和结论，但必须脱敏。

## 7. 文档未到时后端可以做什么

- 定义我方需要的业务能力和方向，本清单就是第一版；
- 为会员中心、门店主数据和 POS 建立适配器边界草案；
- 使用 Mock 服务演练成功、失败、超时、重复和未知结果；
- 设计内部业务编号和幂等原则；
- 继续盘点现有代码复用范围。

文档未到时不应做的事情：

- 自行发明对方正式 URL、签名算法和错误码并写死；
- 把 Mock 联调通过写成“已完成甲方系统对接”；
- 在撤销、对账口径未确认时完成不可逆的数据模型；
- 因为接口字段未定就让全部开发人员无限期等待。

## 8. 给甲方 IT 的简化询问版本

> 为完成一期会员领券、门店核销和补贴明细功能，请协助确认：会员身份如何校验；门店主数据如何取得；POS 能否接入平台的验券、核销、原结果查询和撤销接口；核销结果是否可以按日提供对账数据。请同时提供测试环境、鉴权方式、错误码、超时重试规则及技术联系人。若部分能力暂不支持，也请明确说明，以便调整一期范围。
