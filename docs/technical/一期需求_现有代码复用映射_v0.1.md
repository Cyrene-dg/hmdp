# 青禾茶饮一期需求与现有代码复用映射 v0.1

> 文档性质：后端技术调研稿，不是详细设计，不代表已经确认排期  
> 输入：第三次范围确认会的模拟结论、当前 `hm-dianping` 代码  
> 目标：回答“哪些保留、哪些改造、哪些新增、哪些停用”  
> 复用原则：复用经过验证的工程能力，不为了凑比例保留错误的领域模型

## 1. 本次后端任务是什么

假设技术负责人将任务分给一名普通后端开发，可以写成：

> 根据一期业务流程盘点现有会员、门店、优惠券及秒杀订单代码，输出复用映射和外部接口依赖。暂不编写正式业务代码，不替产品决定未确认的业务规则。

本任务的完成标准：

1. 一期主流程的每一步都能在表中找到；
2. 现有实现有代码或表结构依据，不凭类名推测；
3. 明确标记保留、改造、新增和停用；
4. 发现的业务缺口转成问题或外部接口依赖；
5. 不把 MQ ACK、Redis 预扣或返回订单号误写成权益发放成功。

## 2. 判断标记

| 标记 | 含义 |
|---|---|
| 保留 | 业务含义基本一致，仅需改名、配置化或小范围封装 |
| 改造 | 技术机制有价值，但数据模型、状态或职责需要变化 |
| 新增 | 当前项目没有对应业务能力 |
| 停用 | 与连锁品牌一期无关，不继续投入；是否物理删除另行决定 |
| 待确认 | 依赖甲方规则、外部接口或技术验证，当前不能定稿 |

## 3. 主流程映射

| 业务步骤 | 现有实现及依据 | 判断 | 一期处理建议 | 主要缺口或风险 |
|---|---|---|---|---|
| 会员登录与身份识别 | `UserServiceImpl` 已有短信登录、访问令牌、刷新令牌；请求通过 `UserHolder` 取得用户 | 改造 | 保留令牌和会话基础；增加会员中心适配层，将外部会员号与平台用户关联 | 当前本地 `tb_user` 是会员主数据，真实项目中通常不能自行认定为甲方会员主档 |
| 门店基础信息 | `Shop` 和 `tb_shop` 已有名称、地址、经纬度、营业时间；`ShopServiceImpl` 有查询和缓存 | 改造 | 保留门店查询、缓存和地理检索；补外部门店编码、直营/加盟属性、营业状态、POS版本 | 当前店铺是点评商户模型，没有品牌组织关系和门店经营属性 |
| 活动创建 | `VoucherController` 可直接新增普通券或秒杀券 | 改造 | 拆分营销活动、权益模板、库存配置；后台接口需要权限控制 | 当前任何调用方都可直接保存，且没有草稿、审核、发布流程 |
| 活动审核与发布 | 当前没有审核记录；`Voucher.status` 只有上架、下架、过期 | 新增 | 增加活动状态机、审核意见、审核人、发布人和操作日志 | 市场、运营、财务分别审核什么仍需写进需求基线 |
| 适用门店配置 | `Voucher` 只有一个 `shopId` | 改造 | 新增活动与门店关系；记录门店参加状态及活动开始后的变更规则 | 无法表达一个总部活动适用于多家直营和加盟门店 |
| 固定补贴配置 | `Voucher` 只有支付金额和抵扣金额 | 新增 | 同一活动加盟店使用统一补贴并写入门店快照；直营固定为 0 | 补贴不是优惠面额，也不能复用 `payValue` 冒充 |
| 活动库存初始化 | `VoucherServiceImpl.addSeckillVoucher` 同时写 MySQL 库存和 Redis 库存 | 改造 | 保留库存装载思路；改为活动发布成功后初始化，并增加重复初始化保护 | 当前创建即写库存，没有审批和发布边界 |
| 活动时间及资格校验 | `SeckillVoucher` 有开始、结束时间；当前 Lua 只检查库存和是否重复领取 | 改造 | 在进入库存预扣前校验活动状态、时间、会员资格；高并发核心规则再决定哪些进入 Lua | 现有异步抢券主路径没有使用开始、结束时间完成业务校验 |
| 流量保护 | `VoucherOrderServiceImpl` 有全局、券级、用户级令牌桶 | 保留 | 改为可配置的活动级、会员级保护，并配合网关策略 | 当前容量和补充速率是代码常量，不能直接声称适合十万券活动 |
| 库存预扣及一人一券 | `seckill.lua` 原子检查库存、用户集合并执行预扣 | 改造 | 保留 Lua 原子机制；Key 从秒杀券改为活动库存及领取资格语义 | 目前只能表达简单的每人一次，不能表达会员等级、门店范围等复杂资格 |
| HTTP 请求幂等 | `X-Request-Id` 与用户、券组成幂等 Key，缓存 PROCESSING/SUCCESS/FAILED | 改造 | 保留请求去重；将“请求已受理”和“权益已到账”分成不同状态 | 当前返回 `orderId` 后即把幂等记录写成 SUCCESS，但异步数据库落单可能尚未完成 |
| 领取申请受理 | 当前预扣成功后创建 `VoucherOrder` 对象并立即返回 `orderId` | 改造 | 创建可持久查询的领取申请编号，响应表达 ACCEPTED/PROCESSING，不直接表达发券成功 | 目前没有领取申请表，也没有状态查询接口 |
| 异步发放消息 | 已有 RabbitMQ 持久化交换机、队列、生产确认、退回回调和定时重试 | 改造 | 保留消息可靠投递能力；消息改成“权益发放命令”，携带活动、会员和申请号 | Publisher ACK 只表示 Broker 接收，不能作为数据库权益生成成功的证据 |
| 消费端事务 | `VoucherOrderTransactionService` 将数据库减库存和写订单放在同一事务，唯一键限制一人一券 | 改造 | 保留事务边界及唯一约束思路；改成创建权益、更新申请状态及必要库存流水 | 当前订单表混有支付、退款、核销字段，却没有对应业务实现 |
| 重复消息处理 | 消费前查订单，唯一索引异常后再次确认已有记录 | 保留/改造 | 以申请号或业务事件号保证消费幂等；避免查询后插入的并发窗口成为唯一保障 | 新领域唯一键可能是活动+会员，而不是券+用户 |
| 发放失败补偿 | 已有死信重试、失败记录和 `compensation.lua` 释放 Redis 库存及用户占位 | 改造 | 保留补偿思想；补偿后必须把领取申请更新为 FAILED，并留下运营可查原因 | 当前死单主要存在 Redis 和日志中，没有面向用户、客服的业务状态闭环 |
| 领取结果查询 | 当前控制器只有抢券接口，没有按订单号查询最终处理结果 | 新增 | 提供领取申请状态查询；小程序可轮询或刷新查看 | 用户现在只能拿到订单号，无法判断数据库是否真正成功 |
| 用户卡包 | 当前没有查询用户可用权益的接口 | 新增 | 提供可用、已使用、已过期、已撤销权益列表和详情 | 需要明确券码生成、防猜测及敏感字段展示规则 |
| POS 验券 | 当前没有 POS 或门店员工接口 | 新增 | 根据券码、门店、会员和时间验证是否可用，但不改变权益状态 | 需要 POS 鉴权、门店映射、错误码和访问网络信息 |
| POS 核销 | `VoucherOrder.status/useTime` 只是预留字段，没有核销服务和接口 | 新增 | 新建核销流水，使用 POS 请求号幂等地把权益从 AVAILABLE 改为 USED | 不能因为实体有“已核销”字段就认为功能已经存在 |
| 核销结果查询 | 当前没有 | 新增 | POS 超时后用原请求号查询，返回第一次处理结果 | 这是避免重复核销的 P0 接口 |
| 核销撤销 | 当前没有 | 新增/待确认 | 暂按当天原单撤销建模；是否恢复权益和结算状态等待业务及 POS 能力确认 | 不得在规则未定时直接实现“把 USED 改回 AVAILABLE” |
| 补贴明细 | 当前没有直营/加盟属性、补贴规则和结算流水 | 新增 | 仅加盟店成功核销生成补贴候选；直营只参与 T+1 对账 | 不能在结算时读取可修改的活动当前值重新计算历史金额 |
| POS 数据核对 | 当前没有 | 新增/待确认 | 平台和 POS 均成功的记录进入待结算；差异记录冻结 | POS 对账数据如何取得尚未确认 |
| 结算批次与导出 | 当前没有 | 新增 | 按活动、门店、期间形成批次和 Excel/CSV 明细；一期不自动付款 | 财务样表及字段口径尚未取得 |
| 客服与运营异常查询 | 当前死信只写日志和 Redis 死单记录 | 改造 | 增加按申请号、会员、券码、POS流水查询及人工处理记录 | 权限、脱敏和操作审计待确认 |
| 博客、点赞、关注、Feed、签到 | 现有项目已有完整社区功能 | 停用 | 不纳入青禾一期，不再补功能；物理删除放到后续清理阶段 | 如果继续对外展示，会强化“黑马点评”识别特征 |

## 4. 现有数据模型结论

### 4.1 `tb_shop`

可以作为门店基础表改造的起点，但至少缺少：

- 甲方门店编码；
- 直营/加盟属性；
- 门店启停状态；
- 所属区域或组织；
- POS 厂商及版本；
- 数据同步版本和最后同步时间。

点评项目中的均价、销量、评论数、评分不是一期核心字段，不应继续主导门店模型。

### 4.2 `tb_voucher` 与 `tb_seckill_voucher`

当前结构把券定义、所属单店和秒杀库存绑在一起。一期至少需要区分：

1. 营销活动：谁创建、什么时候开始、总预算、审核和发布状态；
2. 权益模板：发给用户的是什么、使用规则和有效期；
3. 活动门店：哪些门店参加、是否加盟、补贴金额；
4. 活动库存：可发总量、已预留量、已发放量和补偿记录。

不能只给 `tb_voucher` 追加十几个字段解决所有问题。

### 4.3 `tb_voucher_order`

当前表名和字段以“购买代金券订单”为中心，包括支付、退款和核销状态。一期免费权益业务更适合拆成：

- 领取申请；
- 用户权益；
- 核销流水；
- 补贴/结算明细。

具体是否四张表需要在详细设计阶段评审，但至少不能继续用一个订单状态同时表达异步发放、券可用、核销和结算。

## 5. 建议的模块边界草案

| 模块 | 主要职责 | 复用程度初判 |
|---|---|---|
| 身份接入 | 访问令牌、会员身份映射、登录态 | 中高 |
| 门店中心 | 门店同步、直营/加盟属性、门店查询 | 中 |
| 营销活动 | 活动草稿、审核、发布、门店范围、预算 | 低，主要新增 |
| 权益发放 | 资格校验、库存预扣、幂等、MQ发放、补偿、状态查询 | 高，但需重构领域语义 |
| 权益账户 | 用户卡包、有效期、券码、权益状态 | 低，主要新增 |
| 门店履约 | POS验券、核销、查询、撤销 | 低，主要新增 |
| 对账结算 | 补贴明细、差异、批次、导出 | 低，主要新增 |
| 平台基础 | Redis、RabbitMQ、统一异常、日志、限流、缓存 | 高 |

因此，“复用约 60%～70%”应理解为有效后端机制和工程基础的复用目标，不是 60%～70% 的旧接口、旧表名或旧业务代码原封不动保留。

## 6. 当前最重要的技术发现

1. 现有异步抢券返回的是订单号，缺少最终业务状态查询；
2. HTTP 幂等 SUCCESS 目前更接近“请求已受理”，不是“权益已到账”；
3. RabbitMQ Publisher ACK 后会清理生产侧待发送记录，但 ACK 不代表消费者已经写库；
4. `VoucherOrder` 虽然存在核销和退款字段，项目中没有对应业务闭环；
5. Lua 只完成库存和一人一券，不负责活动审批、会员资格、门店范围或补贴；
6. 当前技术能力值得保留，但核心聚合和状态模型必须重画。

## 7. 下一步，不是立即编码

1. 产品根据会议结论确认活动、领取、权益、核销和结算的状态规则；
2. 后端依据《外部系统接口需求清单》向甲方 IT 索取能力和文档；
3. 接口材料到达后，优先验证会员身份、POS 原结果查询、POS 撤销和对账数据获取；
4. 需求与接口结论稳定后，再输出表结构、API 详细设计和迁移方案；
5. 最后才拆开发任务，不能从修改 `VoucherOrderServiceImpl` 类名开始。
